## Этап 4. Анализ исполняемого файла и фикс
Исследуйте таблицу символов полученного исполняемого файла.
Подсказка:
nm app | grep system_mode
Вопросы:
9. В какой секции (.data или .bss) в итоге оказался system_mode в финальном исполняемом файле? Как вы думаете, почему компоновщик сделал именно такой выбор?
```
nm app | grep system_mode
0000000000004020 D system_mode
```
Одно D и два C? сильное определение всегда побеждает независимо от порядка файлов в командной строке. Линковщик просто размещает финальный символ именно туда, а C из legacy.o/hotfix.o ссылаются на ту же ячейку памяти, вместо того чтобы получить отдельное место в .bss.

Современный стандарт разработки требует избегать слабых определений. Пересоберите проект, явно запретив COMMON-символы:
gcc -fno-common main.o hotfix.o legacy.o core.o -o app_better
Вопросы:
10. Какое сообщение об ошибке теперь выдает компоновщик? Как, не меняя имена переменных, можно исправить hotfix.c, чтобы эта сборка прошла успешно?
```
/usr/bin/x86_64-linux-gnu-ld.bfd: warning: alignment 1 of normal symbol `system_mode' in hotfix.o is smaller than 4 used by the common definition in legacy.o
/usr/bin/x86_64-linux-gnu-ld.bfd: warning: NOTE: alignment discrepancies can cause real problems.  Investigation is advised.
/usr/bin/x86_64-linux-gnu-ld.bfd: core.o:(.data+0x0): multiple definition of `system_mode'; hotfix.o:(.bss+0x0): first defined here
collect2: error: ld returned 1 exit status
```

- Компилятор поместил system_mode в .bss с выравниванием 1 байт, а legacy.o (собранный ещё со старым -fcommon) ожидает выравнивание 4 байта для своего COMMON-символа - несовпадение объектных файлов, собранных разными флагами.
- multiple definition of 'system_mode': теперь и core.o (.data), и hotfix.o (.bss) имеют сильные определения одной и той же глобальной переменной. Линковщик теперь не может выбирать, поэтому он останавливается с ошибкой.

Переменная определена сразу в нескольких единицах трансляции, а нужна она hotfix.c только для использования, а не для владения памятью. Значит можно объявить её как extern на core.o, вместо повторного определения:

``` c
extern char system_mode[4];

void apply_hotfix(void) {
  system_mode[0] = 'A';
  system_mode[1] = 'B';
  system_mode[2] = 'C';
  system_mode[3] = '\0';
}
```
Теперь hotfix.o вообще не создаёт собственного символа system_mode, а просто использует то определение, что уже есть в core.o
